# PBI Template Requirement

check-requirement.md のチェックを通過しやすい Requirement チケットの雛形を出力します。

## コマンド形式

```
/pbi:template-requirement [--title "タイトル"]
```

| 引数 | 説明 |
|-----|------|
| `--title "タイトル"` | タイトルをあらかじめ埋めた状態で出力 |
| （省略） | 全フィールドが空欄の雛形を出力 |

---

## 使い方

1. このコマンドを実行すると、下記テンプレートを出力します
2. `[...]` で囲まれた部分を実際の内容に置き換えてください
3. 記載後に `/pbi:check-requirement` で品質確認してください

---

## 空・雨・傘における位置づけ

Requirement は「空・雨・傘」フレームワークの **雨（解釈）に対する傘（対応）を決める層** です。

```text
空（事実）  ←── Needs/Tech/Bug「事実（空）」
雨（解釈）  ←── Needs/Tech/Bug「解釈（雨）」
     ↓ 解釈をもとに対応策を定義する ← ここが Requirement
傘（対応）  ←── Requirement「解決内容」
     ↓ 傘（対応策）をユーザー視点の仕様として展開する
Story       ←── 受け入れ条件（Gherkin形式）
```

**Requirementの役割**: Issue（Tech/Needs/Bug）で読み取った「何が問題か（雨）」を受けて、「何を解決するか（傘）」を決める。実装の詳細（How）には踏み込まない。

---

## 出力テンプレート

以下のテンプレートをそのまま出力する：

```markdown
# [Requirementタイトル]
<!-- Title形式: 「〇〇のために△△できる」または「〇〇は△△にする」-->
<!-- NG例: 「予約変更を改善する」（作業形式） / 「予約変更をWeb完結したい」（願望形式） -->
[対象]のために[解決の方向性]できる

## 元Issue
<!-- 必須: 派生元Issue（Tech / Needs / Bug のいずれか）の#xxxを記載 -->
<!-- NG: Request（RequestはTask直行ルートであり、Requirementを経由しない） -->
【元Issue】[#xxx（Tech / Needs / Bug）]

## 解決内容
<!-- 必須: 元Issueの事実・背景から何を解くべきかの解釈と、その対応策（傘） -->
<!-- NG: 「もっと使いやすくする」「改善する」（曖昧表現） -->
<!-- OK: 「Web画面から日時変更を完結できるようにし、電話対応を不要にする」 -->
[事実・背景] から、[こう解決すべきだ] と考える。

## 別解釈の可能性（推奨）
<!-- check-requirement.md #6 に対応。他の解決の方向性があれば明示する -->
（ただし [別の解決の方向性] もありうる。[採用した理由]）

## Story/Task分解の見込み（任意）
- [ ] Story: [〇〇は△△できる]
- [ ] Task: [〇〇を△△する]
```

---

## Refinement で必ず行うこと

このテンプレートに書き込む前に、Refinement で以下を済ませる:

1. **元Issueの事実・背景の再確認**: Requirementは元Issueの事実・背景の範囲内で解決の方向性を決める。事実・背景にない新たな問題を持ち込まない
2. **Howへの踏み込み禁止**: 「何を解決するか」までを記載し、「どう実装するか」はStory/SubTaskに委ねる
3. **別解釈の検討**: 採用しなかった解決の方向性があれば記録し、後から別の判断をしやすくする

| プロパティ | 値 | 設定タイミング |
|-----------|-----|-------------|
| Type | Requirement | 作成時 |
| Status | Refining | 作成時 |
| Owner | Product | 作成時（全期間Product） |

## check-requirement.md チェック項目との対応

| チェック項目 | テンプレートの対応箇所 |
|------------|----------------------|
| 0-1 Status有効値 | プロパティ設定ガイド参照 |
| 0-3 元Issue種別の確認 | `## 元Issue` セクション（Tech/Needs/Bugのいずれか） |
| 1 Title形式 | 1行目（「〇〇のために△△できる」等） |
| 2 元Issueリンク | `## 元Issue` セクション |
| 3 解決内容の存在 | `## 解決内容` セクション |
| 6 別解釈の言及 | `## 別解釈の可能性` セクション |
| 7 Story/Task分解可能性 | `## Story/Task分解の見込み` セクション |

## よくある記載ミス

| ミスのパターン | 正しい書き方 |
|-------------|------------|
| Title: 「予約変更を改善する」 | 「予約変更はWeb画面から完結できるようにする」（解決の方向性を明示） |
| 元Issueリンクなし | 「【元Issue】#xxx」を必ず記載 |
| 元IssueがRequest | RequestはRequirementを経由しない。Task直行ルートを使う（`check-request.md` 参照） |
| 解決内容: 「もっと使いやすくする」 | 具体的な対応策（「Web画面から〜できるようにする」等）を記載 |
| Howまで記載（「PUT /reservations/{id} を実装する」） | HowはStory/SubTaskに委ねる。Requirementは「何を解決するか」まで |
