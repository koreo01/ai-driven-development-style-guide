# PBI Check Narrative Flow Agent

Narrative Flow（任意の抽象化層）チケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-narrative-flow [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/narrative-flow-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のNarrative Flowチケットをチェック
/pbi:check-narrative-flow #123

# チェック結果をファイルに保存
/pbi:check-narrative-flow #123 --save

# 対話モード
/pbi:check-narrative-flow
```

## Narrative Flow の位置づけ

Narrative Flow は **Story を1段抽象化した、任意の物語の流れ** です。複数の Story を大きな機能単位でまとめる役割を持ちます。

```text
Requirement（傘：対応の方向性）
     ↓ 対応策をユーザー視点の仕様として展開する
Story（What Specified）──┐
Story（What Specified）──┼─ 複数の Story を機能単位で束ねる ← ここが Narrative Flow
Story（What Specified）──┘
     ↑
Narrative Flow（物語の流れ）
     ↑（任意でさらに1段抽象化）
Backbone（物語の骨格）
```

**Narrative Flowの役割**: 個別の Story（「ユーザーは〇〇できる」）をまとめ、「ユーザーは△△という一連の体験ができる」という機能領域の抽象度で物語を記載する。Narrative Flow 自体に Gherkin 形式の受け入れ条件は不要（受け入れ条件は子 Story 側の責務）。

Narrative Flow は任意の抽象化層であり、以下の2方向で作られる:

- **トップダウン**: Narrative Flow を先に定義し、そこから複数の Story に分解する
- **ボトムアップ**: 複数の Story ができた後に、それらを束ねる Narrative Flow を後付けで定義する

### Statusライフサイクル

Narrative Flow のStatusは以下の値のみが有効。パワポ資料に明示の記載がないため、Story群の進行度を表す軽量なライフサイクルとして設計したものである。

```
Draft → Active → Done
```

| Status | 意味 | Owner目安 |
|--------|------|----------|
| Draft | 構想中・子Storyを整理中 | Product |
| Active | 子Storyが開発中 | Product |
| Done | すべての子Storyが完了 | Product |

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| ユーザーは〇〇できる（機能領域の抽象度） | 「ユーザーは対象データをファイリングできる」「ユーザーは対象データを検索できる」 |

### 他のチケットTypeとの違い

| 観点 | Story | **Narrative Flow** | Backbone |
|------|-------|-------------|-----------|
| 抽象度 | What Specified（具体的な振る舞い） | **機能単位の物語（Storyを束ねる）** | 物語の骨格（Narrative Flowをさらに束ねる） |
| 受け入れ条件 | Gherkin形式（必須） | **不要（子Storyが持つ）** | 不要 |
| 子チケット | SubTask | **Story（複数）** | Narrative Flow（複数）または Story（直接） |
| 起票タイミング | Requirement分解時 | **トップダウンまたはボトムアップ（任意）** | トップダウンまたはボトムアップ（任意） |

## チェック対象テンプレート

### Narrative Flowの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | 「ユーザーは〇〇できる」形式（機能領域の抽象度） | 「ユーザーは対象データをファイリングできる」 |
| **子Story** | 束ねる対象のStoryへのリンク（最低1件、推奨2件以上） | 【子Story】#xxx, #yyy |

### Narrative Flowテンプレート

```
【概要】
[この物語の流れが束ねる機能領域を1〜2文で説明]

【子Story】
- [ ] #xxx（タイトル）
- [ ] #yyy（タイトル）

【親Backbone】（任意）
【親Backbone】[#xxx または 無し]
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Draft / Active / Done のいずれか |
| 0-2 | Ownerの設定 | Product が設定されている |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | 「ユーザーは〇〇できる」形式（機能領域の抽象度） |
| 2 | 子Storyの存在 | 子Storyへのリンクが1件以上ある |
| 3 | 概要の存在 | この物語の流れが束ねる機能領域の説明がある |

### Phase 2: 抽象度チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | Gherkin混入なし | 受け入れ条件（Given/When/Then）がNarrative Flow自体に記載されていない |
| 5 | 抽象度の適切性 | Titleが個別の画面操作ではなく機能領域を表している（例: 「検索できる」は適切、「検索ボタンを押すと一覧が表示される」はStory側の記述） |
| 6 | 子Story件数 | 子Storyが2件以上ある（推奨。1件のみの場合はNarrative Flowとして束ねる意味が薄いため⚠️） |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 7 | 単一責任 | 1つのNarrative Flowが1つの機能領域に対応 |
| 8 | 子Storyとの整合性 | 子Storyのタイトルがいずれも同一機能領域に属している |

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 機能領域の抽象度 | `ユーザーは〇〇できる`（〇〇が複数の操作を束ねる機能領域） |
| ⚠️ 個別操作の抽象度（Story相当） | `ユーザーは△△ボタンを押すと〇〇が表示される`（具体的すぎる） |
| ❌ 設計仕様混入 | API名・DB・画面名などの実装詳細が含まれる |

### 子Story件数の判定

| 判定 | パターン | 対応 |
|------|---------|------|
| ✅ 適切 | 子Storyが2件以上 | そのままOK |
| ⚠️ 要検討 | 子Storyが1件のみ | Narrative Flowとして束ねる意味があるか再確認（1件ならStoryのまま運用も可） |
| ❌ なし | 子Storyへのリンクがない | 子Storyを追加するか、Narrative Flow自体の起票が早すぎないか確認 |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 15点 | Status・Ownerの設定 |
| 構造チェック | 30点 | Title形式・子Story・概要の存在 |
| 抽象度チェック | 35点 | Gherkin混入なし・抽象度の適切性・子Story件数 |
| 品質チェック | 20点 | 単一責任・子Storyとの整合性 |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | このまま運用できる |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから運用する |
| 0-59 | ❌ 要リライト | 子Storyの再整理から見直し |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
ユーザーは対象データをファイリングできる

# 概要
対象データをフォルダに整理・移動・タグ付けする一連の体験をまとめる。

# 子Story
- [ ] #201 ユーザーはフォルダを作成できる
- [ ] #202 ユーザーは対象データをフォルダに移動できる
- [ ] #203 ユーザーは対象データにタグを付与できる
```

### 悪い例 ❌

```markdown
# Title
ファイリング機能を実装する

# 子Story
（記載なし）
```

**問題点:**
- Title: 実装形式（「〜を実装する」）→ Narrative Flowは物語の流れを表す形式ではない
- 子Story: リンクなし（何を束ねているのかわからない）

---

## 注意事項

- このAgentは**フォーマット準拠**と**抽象度の適切性**を主眼としています
- Narrative Flow は**任意の抽象化層**であり、必ず作る必要はない。複数Storyの関連が薄い場合は作らずに運用してよい
- **Narrative FlowにGherkin形式は不要**: 受け入れ条件は子Story側の責務
- 子Storyの受け入れ条件の妥当性（本当にこの仕様で良いか等）は判定しません
- Title形式が「実装形式」の場合、Story/SubTask側の記述である可能性を指摘します
