# PBI Check Requirement Agent

Requirement（要件）チケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-requirement [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/requirement-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のRequirementチケットをチェック
/pbi:check-requirement #123

# チェック結果をファイルに保存
/pbi:check-requirement #123 --save

# チェック結果をGitHub Issueにコメント追記
/pbi:check-requirement #123 --gh-comment

# 対話モード
/pbi:check-requirement
```

## 空・雨・傘における位置づけ

Requirement は「空・雨・傘」フレームワークの **雨（解釈）に対する傘（対応）を決める** 層です。

```text
空（事実）  ←── Needs/Tech/Bug「事実（空）」：観察・発言・記録などの生データ
     ↓ 事実をもとに意味を読み取る
雨（解釈）  ←── Needs/Tech/Bug「解釈（雨）」：事実から何を読み取るかの推論
     ↓ 解釈をもとに対応策を定義する ← ここが Requirement
傘（対応）  ←── Requirement「解決内容」：雨（解釈）への具体的な対応策
     ↓ 対応策をユーザー視点の仕様として展開する
Story       ←── 受け入れ条件：傘（対応）の「誰が・何をできるか」
```

**Requirementの役割**: Issue（Tech/Needs/Bug）に書かれた雨（解釈）を受けて「**何を解決すべきか（対応の方向性）**」を決める。Why（なぜ困っているか）から What（何を解決するか）へ翻訳する層です。

## Requirement（What）の位置づけ

```
Issue (Why)                    Requirement (What)        Story/Task (What Specified)
┌─────────┐                   ┌─────────────┐          ┌─────────────────────┐
│  Tech   │──(機能解決)───────→│             │─────────→│ Story               │
│  Needs  │──(機能解決)───────→│ Requirement │          │ (Requirement Spec)  │
│  Bug    │──(仕様変更あり)────→│             │          └─────────────────────┘
└─────────┘                   │             │─────────→┌─────────────────────┐
                               └─────────────┘          │ Task                 │
                                                         │ （仕様化不要な場合） │
                                                         └─────────────────────┘
```

**Requirement** = 「Issueの事実・背景から導かれた解決の方向性」

> ℹ️ Request Issue は Requirement を経由しない（Request→Task 直行ルート）。Requirement に紐づく元 Issue は Tech / Needs / Bug のいずれかに限る（`check-request.md` 参照）。

### Statusライフサイクル

RequirementのStatusは以下の値のみが有効。Issue系（Tech/Needs/Bug）が持つ `Triage` はRequirementには存在しない（元IssueのTriageを通過した後にRequirementが起票されるため）。

```
Refining → Story Defined → In Sprint → Done
```

| Status | 意味 | Owner目安 |
|--------|------|----------|
| Refining | 解決の方向性を精査中 | Product |
| Story Defined | Story / Task 起票済み | Product |
| In Sprint | 対応作業中 | Product |
| Done | 完了 | Product |

> ⚠️ 本ステータス定義は、パワポ資料に明示の記載がないため、既存の `check-needs.md` 等のライフサイクルとの一貫性を優先して設計したものである。Requirementの起票者が「Issueを分析した開発者・プロダクト担当者」であるため、Ownerは全期間 Product とする（Needs/Tech/Bugと異なりBusinessが関与する期間はない）。

### Title/Summary のパターン

| パターン | 例 |
| --- | --- |
| 〇〇のために△△できる | 「予約変更の手戻りを減らすために、変更期限を超えた操作を事前にブロックできる」 |
| 〇〇は△△にする | 「予約変更はWeb画面から完結できるようにする」 |

### 他のチケットTypeとの違い

| 観点 | Needs/Tech/Bug | **Requirement** | Story |
|------|-------|-------------|-----------|
| **空・雨・傘** | 空（事実）＋雨（解釈） | **傘（対応の方向性）** | 傘（対応の仕様展開） |
| 起点 | 顧客の要望・開発者の課題・不具合 | **Issue分析の結果** | Requirement分解の結果 |
| Title形式 | 「〇〇したい」「〇〇がやりづらい」等 | **「〇〇のために△△できる」「〇〇は△△にする」** | 「〇〇は△△できる」 |
| 必須情報 | 事実・解釈 | **元Issue・解決内容** | 受け入れ条件（Gherkin） |
| 抽象度 | Why（なぜ困っている） | **What（何を解決する）** | What Specified（具体的にどう動く） |
| 実装可能性 | × | **△（Story/Taskに分解可能）** | ◎（SubTaskに分解可能） |

## チェック対象テンプレート

### Requirementの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | 「〇〇のために△△できる」または「〇〇は△△にする」形式 | 「予約変更はWeb画面から完結できるようにする」 |
| **元Issue** | 派生元Issue（Tech/Needs/Bugのいずれか）へのリンク | 【元Issue】#xxx |
| **解決内容** | 雨（解釈）への具体的な対応策（傘） | Web完結のための画面・API追加 |

### Requirementテンプレート

```
【元Issue】[#xxx（Tech / Needs / Bug のいずれか）]

【解決内容】
[元Issueの事実・背景から何を解くべきかの解釈と、その対応策]

【別解釈の可能性】（推奨）
（ただし [別の解決の方向性] もありうる。）

【Story/Task分解の見込み】（任意）
- [ ] Story: 〇〇は△△できる
- [ ] Task: 〇〇を△△する
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Refining / Story Defined / In Sprint / Done のいずれか |
| 0-2 | Ownerの設定 | Product が設定されている |
| 0-3 | 元Issue種別の確認 | 元Issueが Tech / Needs / Bug のいずれかである（Requestの場合はフロー誤り） |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | 「〇〇のために△△できる」または「〇〇は△△にする」形式 |
| 2 | 元Issueリンク | Tech/Needs/Bugへのリンクまたは参照がある |
| 3 | 解決内容の存在 | 雨（解釈）への対応策（傘）が記載されている |

### Phase 2: 内容品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | 事実・背景との整合性 | 元Issueに記載された事実・背景を踏まえた内容になっている |
| 5 | 解決の方向性の具体性 | 曖昧な表現（「改善する」「良くする」等）がない |
| 6 | 別解釈の可能性言及（推奨） | 「ただし〜という解決策もありうる」等の記載がある |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 7 | Story/Task分解可能性 | このRequirementからStoryまたはTaskに分解可能か |
| 8 | 単一責任 | 1つのRequirementが1つの解決方向性に対応 |
| 9 | What止まりであること | 実装の詳細（How）まで踏み込んでいない（Howは Story/SubTask側の責務） |

## 出力ファイル

### `--save` オプション使用時

出力先: `analysis/format-check/YYYY-MM-DD_<ticket-id>.md`

```markdown
# フォーマットチェック結果

- **チケット**: #150「予約変更はWeb画面から完結できるようにする」
- **元Issue**: #100「デプロイに時間がかかる」
- **チェック日時**: 2026-10-04 10:00
- **スコア**: 75/100（⚠️ 要改善）

## 指摘事項

### ⚠️ 解決の方向性が曖昧
- 箇所: 解決内容
- 現在の記載: `予約変更をもっと使いやすくする`
- 対応: 具体的な対応策を記載する

### ❌ 別解釈の言及なし
- 対応: 他の解決の方向性があれば追記する

## 次のアクション

1. [ ] 解決の方向性を具体化する
2. [ ] 別解釈の可能性を追記する
3. [ ] 修正後に再度 `/pbi:check-requirement` で確認
```

GitHub Issue のコメントに以下が追記されます：

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 解決の方向性形式 | `〇〇のために△△できる`, `〇〇は△△にする` |
| ❌ 願望形式 | `〜したい`（→ Needsの可能性） |
| ❌ ユーザーストーリー形式 | `〇〇は△△できる`（主語がユーザー、仕様展開済み）（→ Storyの可能性） |
| ❌ 作業形式 | `〇〇を実装する`, `〇〇を修正する`（→ Story/SubTaskのHowの可能性） |

### 元Issue種別の判定

| 判定 | パターン | 対応 |
|------|---------|------|
| ✅ 正常 | 元IssueがTech/Needs/Bugのいずれか | そのままOK |
| ❌ フロー誤り | 元IssueがRequest | RequestはTask直行ルートであり、Requirementを経由しない（`check-request.md` 参照）。Task化を提案 |

### 解決の方向性の具体性判定

| 検出パターン | 改善例 |
|-------------|--------|
| `〜を改善する`, `〜を良くする` | 具体的な対応策を記載 |
| `〜を最適化する` | 何をどう変えるかを具体的に記載 |
| `〜に対応する` | 対応内容を具体的に記載 |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 20点 | Status・Owner・元Issue種別の設定 |
| 構造チェック | 25点 | Title形式・元Issue・解決内容の存在 |
| 内容品質チェック | 30点 | 事実背景との整合性・具体性・別解釈の言及 |
| 品質チェック | 25点 | Story/Task分解可能性・単一責任・What止まり |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | Story/Task分解へ進める |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから進める |
| 0-59 | ❌ 要リライト | 元Issueの事実・背景から見直し |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
予約変更はWeb画面から完結できるようにする

# 元Issue
【元Issue】#100「予約変更の電話対応に時間がかかる」（Tech）

# 解決内容
現在は予約変更のたびに電話対応が発生し、1件あたり平均15分の工数がかかっている
（#100の事実より）。Web画面から日時変更を完結できるようにし、電話対応を
不要にする。

# 別解釈の可能性
（ただし、電話対応自体を残したまま対応時間を短縮する解決策もありうる。
 今回はWeb完結による工数ゼロ化を優先する。）

# Story/Task分解の見込み
- [ ] Story: ユーザーはWeb画面から予約日時を変更できる
```

### 悪い例 ❌

```markdown
# Title
予約変更を改善する

# 解決内容
もっと使いやすくする
```

**問題点:**
- Title: 「改善する」は作業形式に近く、何を解決するのかが不明確
- 元Issue: リンクなし（トレーサビリティ欠如）
- 解決内容: 「もっと使いやすくする」は曖昧。具体的な対応策がない

---

## 注意事項

- このAgentは**フォーマット準拠**と**解決の方向性の具体性**を主眼としています
- 解決策の妥当性（本当にこの方向性で良いか等）は判定しません
- **RequirementにGherkin形式は不要**: 受け入れ条件はStory側の責務
- **RequestはRequirementを経由しない**: 元Issueが Request の場合はフロー誤りとして指摘する
- Title形式が「願望形式」「ユーザーストーリー形式」の場合、Needs/Storyへの変更を提案します
