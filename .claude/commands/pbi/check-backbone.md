# PBI Check Backbone Agent

Backbone（任意の抽象化層）チケットが適切なフォーマットで記載されているかをチェックするガードレールです。

## コマンド形式

```
/pbi:check-backbone [source] [options]
```

### ソース指定方法

| 形式 | 説明 | 例 |
|------|------|-----|
| `@file` | ローカルMDファイル | `@docs/issues/backbone-001.md` |
| `#NUMBER` | GitHub Issue 番号 | `#123` |
| （省略） | 対話モード | - |

### 出力オプション

| オプション | 説明 | 出力先 |
|-----------|------|--------|
| `--save` | チェック結果をMDファイルに保存 | `analysis/format-check/YYYY-MM-DD_<ticket-id>.md` |
| `--gh-comment` | GitHub Issue にコメントとして追記 | 対象 GitHub Issue のコメント欄 |
| （省略） | 画面表示のみ | - |

### 使用例

```bash
# GitHub Issue のBackboneチケットをチェック
/pbi:check-backbone #123

# チェック結果をファイルに保存
/pbi:check-backbone #123 --save

# 対話モード
/pbi:check-backbone
```

## Backbone の位置づけ

Backbone は **Narrative Flow をさらに1段抽象化した、物語の骨格となる任意の抽象化層** です。プロダクト全体の骨格を表します。

```text
Backbone（物語の骨格）
  ├─ Narrative Flow（物語の流れ）
  │    ├─ Story
  │    └─ Story
  └─ Narrative Flow（物語の流れ）
       ├─ Story
       └─ Story
```

**Backboneの役割**: 複数の Narrative Flow（または、Narrative Flow を介さず直接複数の Story）を束ね、プロダクト全体における大きな機能カテゴリを表す。Backbone 自体に Gherkin 形式の受け入れ条件は不要。

Backbone は Narrative Flow と同様、任意の抽象化層であり、トップダウン（Backboneを先に定義してNarrative Flow/Storyに分解する）・ボトムアップ（複数のNarrative Flowができた後に束ねる）のいずれでも作成できる。

### Statusライフサイクル

Backbone のStatusは以下の値のみが有効。Narrative Flow と同一のライフサイクルを採用する。

```
Draft → Active → Done
```

| Status | 意味 | Owner目安 |
|--------|------|----------|
| Draft | 構想中・子Narrative Flow/Storyを整理中 | Product |
| Active | 子チケットが開発中 | Product |
| Done | すべての子チケットが完了 | Product |

### Title/Summary のパターン

| パターン | 例 |
|---------|-----|
| ユーザーは〇〇できる（物語の骨格レベルの抽象度） | 「ユーザーは対象データを編成できる」「ユーザーは対象データを管理できる」 |

### 他のチケットTypeとの違い

| 観点 | Story | Narrative Flow | **Backbone** |
|------|-------|-------------|-----------|
| 抽象度 | What Specified | 機能単位の物語 | **プロダクト全体の骨格** |
| 子チケット | SubTask | Story（複数） | **Narrative Flow（複数）または Story（直接）** |
| 変更頻度 | 高い（スプリント単位） | 中程度 | **低い（プロダクト戦略レベル）** |

## チェック対象テンプレート

### Backboneの必須要素

| フィールド | 必須事項 | 例 |
|-----------|---------|-----|
| **Title** | 「ユーザーは〇〇できる」形式（物語の骨格レベルの抽象度） | 「ユーザーは対象データを編成できる」 |
| **子チケット** | 束ねる対象のNarrative Flow、または直接Storyへのリンク（最低1件、推奨2件以上） | 【子チケット】#xxx, #yyy |

### Backboneテンプレート

```
【概要】
[このBackboneが束ねるプロダクト全体の機能カテゴリを1〜2文で説明]

【子Narrative Flow】（Narrative Flowを介す場合）
- [ ] #xxx（タイトル）
- [ ] #yyy（タイトル）

【子Story】（Narrative Flowを介さず直接Storyを束ねる場合）
- [ ] #xxx（タイトル）
```

## チェックルール

### Phase 0: プロパティチェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 0-1 | Statusの有効値 | Draft / Active / Done のいずれか |
| 0-2 | Ownerの設定 | Product が設定されている |

### Phase 1: 構造チェック（必須）

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 1 | Title形式 | 「ユーザーは〇〇できる」形式（物語の骨格レベルの抽象度） |
| 2 | 子チケットの存在 | 子Narrative Flowまたは子Storyへのリンクが1件以上ある |
| 3 | 概要の存在 | このBackboneが束ねるプロダクト全体の機能カテゴリの説明がある |

### Phase 2: 抽象度チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 4 | Gherkin混入なし | 受け入れ条件（Given/When/Then）がBackbone自体に記載されていない |
| 5 | 抽象度の適切性 | TitleがNarrative Flowよりもさらに広い機能カテゴリを表している（Narrative Flowと同一粒度の場合は⚠️） |
| 6 | 子チケット件数 | 子チケットが2件以上ある（推奨。1件のみの場合は⚠️） |

### Phase 3: 品質チェック

| # | チェック項目 | 合格基準 |
|---|-------------|---------|
| 7 | 単一責任 | 1つのBackboneが1つの機能カテゴリに対応 |
| 8 | 子チケットとの整合性 | 子Narrative Flow/Storyのタイトルがいずれも同一カテゴリに属している |

## パターン検出ルール

### Title形式の判定

| 判定 | パターン |
|------|---------|
| ✅ 物語の骨格レベルの抽象度 | `ユーザーは〇〇できる`（〇〇がNarrative Flow複数を束ねる広さ） |
| ⚠️ Narrative Flowと同一粒度 | Narrative Flow 1件と実質同じ範囲しか束ねていない |
| ❌ 設計仕様混入 | API名・DB・画面名などの実装詳細が含まれる |

### 子チケット件数の判定

| 判定 | パターン | 対応 |
|------|---------|------|
| ✅ 適切 | 子チケットが2件以上 | そのままOK |
| ⚠️ 要検討 | 子チケットが1件のみ | Backboneとして束ねる意味があるか再確認 |
| ❌ なし | 子チケットへのリンクがない | 子チケットを追加するか、起票が早すぎないか確認 |

## スコアリング基準

| Phase | 配点 | 評価観点 |
|-------|------|---------|
| プロパティチェック | 15点 | Status・Ownerの設定 |
| 構造チェック | 30点 | Title形式・子チケット・概要の存在 |
| 抽象度チェック | 35点 | Gherkin混入なし・抽象度の適切性・子チケット件数 |
| 品質チェック | 20点 | 単一責任・子チケットとの整合性 |

### 判定基準

| スコア | 判定 | 推奨アクション |
|--------|------|---------------|
| 80-100 | ✅ Ready | このまま運用できる |
| 60-79 | ⚠️ 要改善 | 指摘箇所を修正してから運用する |
| 0-59 | ❌ 要リライト | 子チケットの再整理から見直し |

## 良い例・悪い例

### 良い例 ✅

```markdown
# Title
ユーザーは対象データを編成できる

# 概要
対象データのファイリング・検索・タグ管理など、データ編成に関わる
機能カテゴリ全体をまとめる。

# 子Narrative Flow
- [ ] #200 ユーザーは対象データをファイリングできる
- [ ] #210 ユーザーは対象データを検索できる
```

### 悪い例 ❌

```markdown
# Title
データ管理機能を実装する

# 子Narrative Flow
（記載なし）
```

**問題点:**
- Title: 実装形式（「〜を実装する」）→ Backboneは物語の骨格を表す形式ではない
- 子チケット: リンクなし（何を束ねているのかわからない）

---

## 注意事項

- このAgentは**フォーマット準拠**と**抽象度の適切性**を主眼としています
- Backbone は**任意の抽象化層**であり、必ず作る必要はない。プロダクト規模が小さい場合は作らずに運用してよい
- **BackboneにGherkin形式は不要**: 受け入れ条件は子Story側の責務
- 子Narrative Flow/Storyの内容の妥当性は判定しません
- Title形式が「実装形式」の場合、下位チケット側の記述である可能性を指摘します
